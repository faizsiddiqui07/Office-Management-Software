## 1. [RED] Re-attaching to a non-owner survivor + clearing forwardedFrom severs chainEligible's upward walk — gate flips true→false on any chain deeper than 2

lens: gate · `D:/React Projects/office-management-software/backend/src/services/bonus.service.js`:567

**Scenario:** Owner tier = {Aamir (CEO)}. Aamir assigns 'Q2 statutory audit', due 2026-08-20, to Manager Priyanshi -> R {owner: Priyanshi, assignedBy: Aamir, forwardedFrom: null}. Priyanshi forwards to Senior Rohit -> T2 {owner: Rohit, assignedBy: Priyanshi, forwardedFrom: R}. Rohit forwards to Junior Sneha -> T3 {owner: Sneha, assignedBy: Rohit, forwardedFrom: T2, collaborators: []}. Sneha delivers 2026-08-18, the chain settles, and onAssignedTaskDone(R) pays the tree: Priyanshi auto_forward:R +3 (forwardOnTime, seeded at bonus.service.js:1582), Rohit auto_forward:T2 +3, Sneha auto_task:T3 +10 (assignedTaskOnTime as configured). On 2026-08-19 Rohit is deleted. GATE BEFORE: chainEligible(T3) = taskEligible(T3) false (Rohit not owner-tier, no tags) -> parent T2 false (Priyanshi not owner-tier) -> parent R true (assignedBy = Aamir) => TRUE. WHAT THE DESIGN DOES: Task.deleteMany({owner: Rohit}) (user.service.js:337) removes T2; the nearest surviving link above Sneha is Priyanshi (R's owner), so T3.assignedBy = Priyanshi and T3.forwardedFrom = null. GATE AFTER: taskEligible(T3) = Priyanshi is not in ownerIds and collaborators is empty -> false; chainEligible has no forwardedFrom left to walk => FALSE. Direction: points DELETED. Sneha loses the full +10, and the loss is deterministic, not theoretical: clearing forwardedFrom moves T3 into rescoreAllDoneAssigned's root set (bonus.service.js:1626 filters forwardedFrom: null), which calls onAssignedTaskDone(T3) that same night; copies = [T3] alone, no copy is eligible, and line 633 hard-deletes every auto_task/auto_forward entry on T3. Setting assignerDeleted does not save it — the award path (bonus.service.js:632) and the rescore never read that flag; only pruneOrphanTaskEntries does (bonus.service.js:1709).

**Verifier:** CONFIRMED. Maine ise refute karne ki poori koshish ki — teen alag raaste se bachne ka scope dhoonda (assignerDeleted escape hatch, 45-din ka rescore cutoff, aur "shayad gate kabhi T3 pe akele evaluate hi nahi hota") — teenon band nikle. Design as stated depth>=3 chain me middle link delete hone par points DELETE karta hai.

GROUND TRUTH (padha hua code):
1. forwardTask (task.service.js:522-532) child banata hai `assignedBy = actor` (= parent.owner) aur `forwardedFrom = parent`. Yaani 3-level chain banna trivially possible hai; loop-guard (task.service.js:515-518) sirf upstream par rok lagata hai, Sneha upstream me nahi hai. chainEligible depth<12 (bonus.service.js:570), collectChainCopies depth<12 (585-596), settleParent depth>10 (559) — yaani 12 tak ki chain first-class supported hai, 3-deep koi corner case nahi.
2. taskEligible (bonus.service.js:555-560) sirf `task.assignedBy` aur `task.collaborators` dekhta hai — upar nahi chalta. chainEligible (567-583) ka poora upward walk `cur.forwardedFrom` par chalta hai. forwardedFrom clear kar do to walk ka fuel hi khatam.

SCENARIO (objection wala, verify kiya):
Owner tier = {Aamir}. R{owner:Priyanshi, assignedBy:Aamir, forwardedFrom:null} -> T2{owner:Rohit, assignedBy:Priyanshi, forwardedFrom:R} -> T3{owner:Sneha, assignedBy:Rohit, forwardedFrom:T2, collaborators:[]}. Sneha 18-Aug delivers, chain settle, onAssignedTaskDone(R): copies=[R,T2,T3], gate line 632 R se pass (assignedBy=Aamir), forwarderIds={R,T2} (line 645), to Priyanshi auto_forward:R +3 (forwardOnTime seed, bonus.service.js:1581), Rohit auto_forward:T2 +3, Sneha auto_task:T3 +10 (assignedTaskOnTime, leadership-configured, Setting.js:77-79).
19-Aug Rohit delete. user.service.js:337 `Task.deleteMany({owner: uid})` T2 ko uda deta hai. Design ke hisaab se nearest surviving link = R ka owner Priyanshi, to T3.assignedBy=Priyanshi aur T3.forwardedFrom=null.
GATE BEFORE = TRUE (T3 false -> T2 false -> R true, line 579). GATE AFTER = FALSE (taskEligible false, forwardedFrom null to loop 570 chalta hi nahi). Safety property yahin toot gaya: property tabhi hold karti hai jab nearest surviving link KHUD owner-tier ho, jo sirf 2-level CEO->Manager->Junior me sach hai.

DELETION DETERMINISTIC HAI (yeh maine sabse zyada check kiya):
- forwardedFrom clear hote hi T3 rescoreAllDoneAssigned ke ROOT set me aa jaata hai — bonus.service.js:1626 filter `{status:'DONE', assignedBy:{$ne:null}, completedAt:{$gte: now-45d}, forwardedFrom:null}`. T3 saare 4 satisfy karta hai (completedAt 18-Aug, delete 19-Aug).
- onAssignedTaskDone(T3): line 619 pass (assignedBy=Priyanshi non-null), line 621 pass (forwardedFrom null), collectChainCopies(T3)=[] to copies=[T3], line 632 `!copies.some(taskEligible)` TRUE -> line 633 `PointEntry.deleteMany({taskRef:[T3], source:['auto_task','auto_forward']})`. Sneha ka +10 usi raat gaya.
- assignerDeleted bachata NAHI: maine poore repo me grep kiya, uske sirf 5 hits hain — user.service.js:351 (write), Task.js:14 (schema), aur bonus.service.js:1691/1692/1709 — teenon pruneOrphanTaskEntries ke andar. Award path (632), scanOverdueTasks (1038), rescoreAllDoneAssigned kabhi nahi padhte. Yeh bilkul rejected design (b) wali hi bimari hai.
- 45-din cutoff se bhi escape nahi: agar delete completion ke 45 din baad ho to rescore skip karega, par tab prune line 1709 chalega — agar re-attach ne assignerDeleted set nahi kiya (assignedBy ab non-null hai, to logically set karne ki wajah bhi nahi) to chainEligible(T3)=false -> entry dead (1716). Dono window me nuksaan.

REGRESSION HAI, sirf gap nahi: aaj ke code me T3.forwardedFrom dangling rehta hai, isliye T3 root set (1626) me aata hi nahi aur prune use assignerDeleted ki wajah se spare kar deta hai (1709) — Sneha ke points aaj ZINDA hain. Proposed design unko maar dega. Yaani yeh fix current behaviour se ULTA hai is case me.

BONUS COLLATERAL (same root cause, same fix): T3 detach hote hi collectChainCopies(R) khaali ho jaata hai, to forwarderIds empty (line 645) aur Priyanshi ka auto_forward:R (+3) line 673 se delete hokar auto_task:R (+10 assignedTaskOnTime) ban jaata hai — 7 points INVENT ho gaye us kaam ke jo usne kiya hi nahi. Objection ka apna caveat "design never invents points" gate ke through sach hai, forwarder/doer classification ke through nahi. Aur agar chain abhi PENDING thi: settleParent(T3) line 559 par turant return karega (forwardedFrom null), to R hamesha PENDING rahegi; saath hi R ab forwardedParentIds (line 1029) me nahi hai, to scanOverdueTasks Priyanshi par -assignedTaskLate mark + roz ka assignedTaskOverdueDaily drip thokna shuru kar dega.

**Design me kya badle:** SABSE CHHOTA BADLAV: re-attach me forwardedFrom CLEAR mat karo — use nearest surviving ANCESTOR TASK par RE-POINT karo, aur assignedBy us task ke owner ko do.

Rule: deleted user ki child copy ke liye forwardedFrom chain upar walk karo jab tak koi aisi ancestor task na mile jo abhi bhi exist karti ho (R). Phir: T3.forwardedFrom = R, T3.assignedBy = R.owner (Priyanshi), plus departed-person ka snapshotted naam note ke liye. Yeh exactly wahi shape hai jo forwardTask khud likhta hai (task.service.js:527-528: child.assignedBy = actor = parent.owner, child.forwardedFrom = parent) — yaani DB me state aisi dikhti hai jaise Priyanshi ne seedha Sneha ko forward kiya ho, koi naya invariant nahi bana.

Isse ek saath yeh sab preserve ho jaata hai:
- chainEligible(T3): T3 -> R -> Aamir = TRUE (bonus.service.js:579). Gate kisi bhi depth par preserved, sirf depth-2 par nahi.
- collectChainCopies(R) T3 ko phir se dhoondh lega, onBonus root R hi rahega: Priyanshi auto_forward +3 aur Sneha auto_task +10 — na koi point deleted, na invented.
- T3 rescoreAllDoneAssigned ke root set (line 1626, forwardedFrom:null) me nahi ghusega, to line 632 ka isolated-gate wipe trigger hi nahi hoga.
- settleParent(T3) (task.service.js:559) upar R tak settle karta rahega; R scanOverdueTasks ke forwardedParentIds exclusion (line 1029) me bani rahegi, to Priyanshi par jhootha overdue drip nahi lagega.
- listTasks ka chain display (task.service.js:1092-1129) chalta rahega; jahan Rohit tha wahan snapshotted naam se "yeh kaam Rohit ke through aaya tha, jo ab ja chuke hain" dikha do.

Design ka existing "clear forwardedFrom" behaviour SIRF us case me lagu ho jab koi ancestor task bachi hi na ho (2-level: Priyanshi delete hui to R bhi Task.deleteMany({owner}) se gayi) — tab child genuinely root ban jaati hai aur assignedBy = deleted root ki assignedBy (Aamir) sahi jawab hai. Yaani "clear" ko default se badal kar fallback bana do.

## 2. [RED] Eligibility carried by a TAG dies with the deleted copy — forwardTask never copies collaborators, so the re-attached child has no tag to inherit

lens: gate · `D:/React Projects/office-management-software/backend/src/services/task.service.js`:522

**Scenario:** Owner tier = {Aamir (CEO)}. Manager Ravi (NOT owner-tier) assigns 'Vendor GST reconcile', due 2026-08-25, to Senior Rohit and tags Aamir for visibility -> R {owner: Rohit, assignedBy: Ravi, collaborators: [Aamir], forwardedFrom: null}. Rohit forwards it to Junior Sneha -> C. Task.create at task.service.js:522-532 sets title/notes/dueYMD/owner/assignedBy/forwardedFrom/originalAssignedBy/requiresApproval and nothing else, so C.collaborators = [] — the tag does not travel down. GATE BEFORE: chainEligible(C) = taskEligible(C) false -> parent R: collaborators contains Aamir -> TRUE (bonus.service.js:559). Award path agrees: copies = [R, C], taskEligible(R) true (bonus.service.js:632), so Sneha's completion pays her +10 assignedTaskOnTime and Rohit +3 forwardOnTime. Rohit resigns and is deleted on 2026-08-20: Task.deleteMany({owner: Rohit}) destroys R and with it the only row that carried Aamir's tag. The design re-attaches C to the nearest surviving link above Rohit, which is Ravi (R.assignedBy). GATE AFTER: taskEligible(C) — Ravi is not in ownerIds, C.collaborators is still [] => FALSE. Direction: points DELETED, Sneha loses the whole +10 (and if the chain had been late, the -5 mark and every -1 drip are REFUNDED out of closed months, which is the mirror error). Note the ordinary tag path is safe for comparison: deleting a tagged owner-tier user leaves their id sitting in Task.collaborators (user.service.js:346-358 pulls uid only from User.taskAssign.users, never from Task.collaborators), but ownerTierIds is built from live User rows (bonus.service.js:530) so the stale id no longer matches — same loss, different door.

**Verifier:** Maine ise refute karne ki poori koshish ki — teen alag darwaze try kiye (tag propagate hota hai kya? CEO ko non-owner tag kar sakta hai kya? re-attached child ko koi aur cheez bacha leti hai kya?) — teenon band nikle. Objection sahi hai.

GROUNDING (jo maine actually padha):

1) Tag forward chain me travel karta hi nahi. forwardTask ka Task.create (task.service.js:522-532) sirf title/notes/dueYMD/owner/assignedBy/forwardedFrom/originalAssignedBy/requiresApproval set karta hai — `collaborators` field list me hai hi nahi, to child ko schema default `[]` milta hai (models/Task.js collaborators default: []). Maine edit-path bhi check kiya, kyunki wahan se tag baad me neeche ja sakta tha: updateTask ka tag block (task.service.js:733-746) sirf `members` par chalta hai, aur `members` = assignBatch siblings (`batchQuery` line 654), forward descendants nahi. Aur jo cascade forward descendants tak jaata hai (line 813-826) wo sirf `contentFields` = title/notes/dueYMD copy karta hai. Matlab ek tag-anchored chain me CEO ka tag SIRF us row par baithta hai jise forward kiya gaya tha.

2) Non-owner assigner CEO ko tag kar sakta hai — ye code me explicitly likha hai. createTask ka comment (task.service.js:162-164): "anyone in the office can be tagged (a CEO too)", aur resolveCollaborators (127-137) sirf existence + isActive check karta hai, rank/role ka koi guard nahi. To scenario legal hai, exotic nahi.

3) Gate ka doosra paer sach me collaborators par khada hai: taskEligible (bonus.service.js:555-560) — `assignedBy in ownerIds` OR `collaborators me koi ownerId`.

SCENARIO (real numbers, real dates):
Owner tier = {Aamir (CEO)}. 03-Aug-2026: Manager Ravi (owner-tier NAHI) "Vendor GST reconcile" (due 2026-08-25) Senior Rohit ko assign karta hai aur Aamir ko tag karta hai → R {owner: Rohit, assignedBy: Ravi, collaborators: [Aamir], forwardedFrom: null}. 05-Aug: Rohit ise Junior Sneha ko forward karta hai → C {owner: Sneha, assignedBy: Rohit, forwardedFrom: R, collaborators: []}.
18-Aug: Sneha done karti hai → settleParent (task.service.js:599) root R band karta hai → onAssignedTaskDone(R). copies = [R, C]; line 632 ka gate `copies.some(taskEligible)` → R.collaborators me Aamir hai → TRUE. Sneha ko auto_task:C par +10 (assignedTaskOnTime, month 2026-08), Rohit ko auto_forward:R par +3.
20-Aug: Rohit resign, delete. user.service.js:337 `Task.deleteMany({owner: uid})` R ko mita deta hai — aur uske saath Aamir ka tag rakhne wali EKMATRA row bhi.
Design ab C ko "nearest surviving link above" = Ravi se jodta hai: C.assignedBy = Ravi, C.forwardedFrom = null.
21-Aug ki nightly: rescoreAllDoneAssigned (bonus.service.js:1626) ka filter hai `status:'DONE', assignedBy: {$ne:null}, forwardedFrom: null, completedAt >= 45d` — re-attach se pehle C teenon me fail hota tha (assignedBy null + forwardedFrom set), re-attach ke BAAD C teenon pass karta hai, to ab wo is pass me aa jaata hai → onAssignedTaskDone(C) → copies = [C] → taskEligible(C): Ravi ownerIds me nahi, collaborators abhi bhi [] → FALSE → line 633 `PointEntry.deleteMany({taskRef: C, source: ['auto_task','auto_forward']})`. Sneha ka poora +10 gayab, closed hone ja rahe August month se.
Doosra darwaza bhi khula hai: pruneOrphanTaskEntries — re-attach ke baad C.assignedBy non-null hai, to line 1709 ka `t.assignerDeleted ? true` escape hatch lagta hi nahi (aur agar design assignerDeleted set bhi kar de, to prune to bach jaayega par award path use padhta hi nahi — wahi rejected design (b) wali failure). Aur line 1716 ka dead-push sign se pehle chalta hai, to LATE variant me -5 mark aur har -1 drip bhi refund ho jaayenge — mirror error.

DO-NO-HARM CHECK (ye sabse important nikla): aaj, bina design ke, ye points ZINDA rehte hain. Delete ke baad C.assignedBy = null + assignerDeleted = true (user.service.js:351); rescoreAllDoneAssigned ka `assignedBy: {$ne: null}` C ko chhod deta hai, onAssignedTaskDone line 619 waise bhi early-return karta, aur prune line 1709 assignerDeleted ki wajah se eligible maan leta hai. Matlab design isko theek nahi kar raha — is class ke liye design ek NAYA regression paida kar raha hai: TRUE → FALSE flip, points delete.

Safety property "re-attaching preserves the gate answer" isliye tootta hai kyunki wo maanta hai ki gate ka jawab ASSIGNER par rakha hai. bonus.service.js:559 kehta hai jawab collaborators par bhi utna hi rakha ho sakta hai, aur forwardTask us evidence ko neeche bhejta hi nahi — to jo row delete ho rahi hai, tag-anchored chain me wahi ekmatra gawaah hai.

CORROBORATION (alag darwaza, objection ne sahi pakda): deleteUser Task.collaborators se uid pull karta hi nahi — line 346-358 me sirf `User.updateMany({'taskAssign.users': uid}, {$pull: ...})` hai (line 357), koi `Task.updateMany({collaborators: uid}, ...)` nahi. Par ownerTierIds live User rows se banta hai (bonus.service.js:530-533), to tagged CEO ka delete hote hi wo stale id kabhi match nahi karega. Ye design ka bug nahi hai (pehle se hai), lekin ye dikhata hai ki tag-as-evidence pehle se hi hawa me lataka hua hai — design use aur tod raha hai.

Scope note: ye failure sirf tab hota hai jab (i) chain tag se eligible thi, aur (ii) "nearest surviving link above" non-owner-tier nikla. Agar upar wala assigner owner-tier hai to gate waise hi TRUE rehta hai aur design theek chalta hai.

**Design me kya badle:** Re-attachment ko "assigner uthao" ki jagah "GATE KE INPUTS uthao" define karo. Jis parent copy ko delete kiya ja raha hai, uske gate-inputs DONO hain: assignedBy aur collaborators. To re-attach step me, assignedBy ke saath-saath us destroy ho rahi parent row ka collaborators set bhi child par union kar do — dedupe karke, child ke apne owner ko aur delete ho rahe uid ko nikaal kar:

  child.assignedBy   = nearest surviving assigner (jaisa design me hai)
  child.forwardedFrom = null (jaisa design me hai)
  child.collaborators = unique(child.collaborators ∪ dyingParent.collaborators) − {child.owner, deletedUid}

Bas itna. Isse taskEligible(child) wahi jawab dega jo pehle chainEligible(child) deta tha, kyunki gate jo cheez padhta hai (bonus.service.js:555-560) wo ab child par maujood hai — na koi point delete hoga, na koi naya banega. Union hone ki wajah se ye recursive bhi safe hai: agar aage chal kar Ravi bhi delete hota hai, to evidence agli re-attach par phir se neeche travel kar jaayega. Ye (a) bhi nahi hai (assigner arbitrary nahi chuna ja raha) aur (b) bhi nahi (koi naya flag nahi jise award path ignore kar sake — same field jise dono path pehle se padhte hain).

Do cheezein design me likh dena, warna implementation galat jagah jaayegi:
1. Blast radius kam rakhna ho to sirf owner-tier subset carry karo (dyingParent.collaborators ∩ ownerTierIds) — gate ke liye utna hi kaafi hai. Poora set carry karne ka side-effect ye hai ki collaborators sirf gate nahi, ACCESS bhi deta hai (task.service.js:258, 270, 356 read-access; 944 aur 1156 "Shared with me" listing) — yaani un logon ko ek aisi row dikhne lagegi jis par wo pehle tagged nahi the. Owner-tier-only variant me ye sirf CEO/President tak simat jaata hai, jinke liye ye visibility wahi hai jo tag ka maqsad tha.
2. Ye union UNHI rows par chale jo re-attach ho rahi hain, aur `Task.deleteMany({owner: uid})` se PEHLE parent ki collaborators list padhi jaaye (delete ke baad evidence chala jaata hai) — yaani delete order design me explicit ho: pehle chain snapshot (parent ka collaborators + departed ka naam), phir delete, phir re-attach.

## 3. [RED] Clearing forwardedFrom moves the payout trigger off the top of the chain: work that could still be rejected is paid, and on-time/late is re-judged from the junior's own completion day

lens: gate · `D:/React Projects/office-management-software/backend/src/services/bonus.service.js`:621

**Scenario:** Owner tier = {Aamir (CEO)}. Aamir assigns 'Ranchi site drawings', due 2026-08-20, requiresApproval TRUE, to Manager Priyanshi -> R {owner: Priyanshi, assignedBy: Aamir, requiresApproval: true}. Priyanshi forwards to Junior Rahul with requiresApproval FALSE -> C {owner: Rahul, assignedBy: Priyanshi, forwardedFrom: R, dueYMD 2026-08-20}. Priyanshi is deleted 2026-08-12; R (owner Priyanshi) is destroyed, and the design re-attaches C to Aamir with forwardedFrom cleared. BEFORE: Rahul taps Done on 19 Aug -> onAssignedTaskDone(C) returns immediately at bonus.service.js:621 (non-root copies never pay), settleParent submits R to Aamir (task.service.js:573-591). If Aamir REJECTS, nobody is ever paid — the documented invariant at bonus.service.js:603-608. If he approves on 22 Aug, reviewTask sets R.completedAt = 22 Aug (task.service.js:408) and lateness is judged on the ROOT: rawYMD 2026-08-22 > 2026-08-20 + graceDays 1 = 2026-08-21, so the chain is LATE and Rahul gets -5 (assignedTaskLate), Priyanshi -2 (forwardLate). AFTER: C is its own root, requiresApproval false, so setStatus closes it and calls onAssignedTaskDone(C) (task.service.js:366); taskEligible(C) is true on Aamir, C is a leaf, rawYMD = 19 Aug <= 21 Aug -> Rahul is paid +10 assignedTaskOnTime on the spot. Aamir never sees it, cannot reject it, and cannot review it (reviewTask needs awaitingApproval, task.service.js:391). Swing on this one task: 0 or -5 becomes +10 — 15 points invented, and the CEO's deliberate approval gate is dissolved because it lived on the destroyed copy.

**Verifier:** Main ne isko refute karne ki poori koshish ki — koi guard nahi mila. Objection sahi hai.

**Code jo isko sach banata hai**

1. `backend/src/services/bonus.service.js:621` — `if (task.forwardedFrom) return;`. Yehi ek line payout ka trigger decide karti hai. `forwardedFrom` set = "main root nahi hoon, upar wale ke accept karne ka wait karo". Null = "main hi root hoon, abhi pay karo".
2. `bonus.service.js:603-608` (docstring) is invariant ko likhkar rakhta hai: "nobody is paid until the work is accepted at the TOP of the chain… a later rejection at the top means C, B and A all get nothing". Aur yeh sirf internal note nahi hai — `backend/src/lib/rulesSeed.js:25` employees ko yehi rule dikhata hai: "Nobody is paid until the task is approved at the top of the chain."
3. `bonus.service.js:647` + `652` — `rawYMD = ymdInTz(task.completedAt)` aur `late` ka faisla usi `rawYMD` par. `reviewTask` approve par `task.completedAt = new Date()` set karta hai (`task.service.js:408`), yaani chain ke liye late/on-time ROOT ke approval din se juda hai, junior ke Done tap se nahi.
4. `backend/src/services/user.service.js:337` — `Task.deleteMany({ owner: uid })`. Priyanshi delete hoti hai to R (approval gate jis copy par baitha tha) sach mein mit jaata hai. Gate ka koi doosra ghar nahi — `requiresApproval`/`submittedAt` sirf us row par the.
5. Design sirf teen cheezein badalta hai: `assignedBy`, `forwardedFrom` clear, aur departed ka naam snapshot. `requiresApproval` ka koi zikr nahi — matlab C apni hi value (false) ke saath root ban jaata hai.

**Scenario (numbers ke saath, config values +10 / −5 / −2 jaise objection mein — actual values `Setting.bonus.autoRules` se aate hain, `bonus.service.js:138 rulePoints`)**

Owner tier = {Aamir (CEO)}. Aamir → Priyanshi: "Ranchi site drawings", dueYMD 2026-08-20, requiresApproval TRUE → R. Priyanshi forward → Rahul, requiresApproval FALSE → C {assignedBy: Priyanshi, forwardedFrom: R, dueYMD 2026-08-20}. graceDays 1 → cutoff 2026-08-21.

Priyanshi 12 Aug ko delete. R destroy. Design C ko Aamir se re-attach karta hai, `forwardedFrom` null.

- *Deletion se pehle wali duniya:* Rahul 19 Aug ko Done → `task.service.js:366` → `onAssignedTaskDone(C)` line 621 par turant return, koi point nahi. `settleParent` (`task.service.js:573-591`) R ko Aamir ke paas submit karta hai. Aamir REJECT kare → kisi ko kuch nahi (0). Aamir 22 Aug ko approve kare → R.completedAt = 22 Aug, `rawYMD 2026-08-22 > 2026-08-21` → LATE → Rahul −5, Priyanshi −2.
- *Design ke baad:* C khud root hai, requiresApproval false → `setStatus` line 314 wali branch skip, status DONE, line 366 par `onAssignedTaskDone(C)`. Line 621 ab return nahi karta. `collectChainCopies` khaali, `taskEligible(C)` Aamir par TRUE (gate ka jawab sach mein preserve hai — wahi to problem hai), `hasScorableDeadline` TRUE, C leaf hai → doer. `rawYMD = 2026-08-19 <= 2026-08-21` → **Rahul ko +10 assignedTaskOnTime, wahi waqt, 19 Aug ko**. Aamir ko notification tak nahi jaata (`settleParent` ka `childTask.forwardedFrom` null hai, line 559 par return), aur wo review kar bhi nahi sakta — `reviewTask` `awaitingApproval` maangta hai (`task.service.js:391`), jo `status === 'PENDING' && submittedAt` par depend karta hai (`models/Task.js:50-52`), aur C DONE hai.

**Design me kya badle:** Add one explicit terminal branch to the design, plus one ordering sentence.

1. That shape means "personal to-do" at task.service.js:276, :314, :642, :843, :864 and bonus.service.js:619, :1030, and every one of those readings is wrong for delegated work.

4. That matches what already happens when an assigner deletes an overdue task, but it should be an accepted consequence, not a surprise.

Two things I checked that do NOT refute it: (1) the doc's freeze section (`08d:88-97`) only covers the delete→accept window, and Rule 1 has no accept step, so nothing is frozen here; (2) the current shipped bug is no better but is not better — today A keeps a dangling `forwardedFrom` and `onAssignedTaskDone` returns at :621, so Aditi also gets nothing. The design's claim is that it FIXES this; at depth 3 with a non-owner survivor it does not.

**Design me kya badle:** Change Rule 1 from "becomes a direct assignment" to "the child INHERITS the departed copy's position in the chain". Concretely, one rule replaces the two-part rule: read the doomed copy's own `assignedBy` and `forwardedFrom` before it is destroyed (i.e. before `Task.deleteMany({ owner: uid })` at user.service.js:337) and copy BOTH onto the child — `child.assignedBy := deletedCopy.assignedBy`, `child.forwardedFrom := deletedCopy.forwardedFrom`. This is strictly stronger than the stated design and needs no new flag:
- Depth 3 (CEO → Priyanshi → Rohit → Aditi, Rohit deleted): A gets assignedBy = Priyanshi AND forwardedFrom = P (P still exists — it was never Rohit's). `chainEligible(A)` walks A → P → `taskEligible(P)` true on Khaan. Gate stays YES by construction, `settleParent` still closes P, and the split stays correct (P has a child again → forwarder award; Aditi → doer award). Rohit's own link is spliced out, which is the only thing that actually disappeared.
- Depth 2 (CEO → Manager → Junior, Manager deleted): the deleted copy WAS the root, so its `forwardedFrom` is null and its `assignedBy` is the CEO — the child correctly becomes a root assigned by the CEO. This is exactly the case the design already got right, now falling out of the same rule instead of being a special case.
- The gate answer is preserved by construction rather than by argument: the child now occupies the exact chain slot that was removed, and everything above it is untouched, so `chainEligible` sees the identical ancestor set minus one node that could never be the eligibility source on its own (if the departed copy WAS the source — e.g. an owner tagged only on Rohit's copy via `collaborators` — no design can preserve that, because the evidence is what got deleted; that case must fall to Rule 3 rather than be silently re-derived).

The "who has since left" name snapshot is unaffected: still stamp the departed person's name on the child for the note; it is display-only and must never be read by the gate.
